# 04 — Atomic Requirements

## MUST requirements

### REQ-BASE-001 — Green inherited baseline

Priority: P0 / Mandatory: MUST / Actor: Maintainer / Trigger: PR-001 verification / Precondition: baseline commit checked out / Input: repository source / Input Validation: lockfile and declared package scripts / Authorization: local developer access / Processing: resolve missing `pg` declarations and unused imports without test suppression / Output: green root check / State Change: dependency metadata and imports only / Side Effects: package lock update if dependency added / Failure Conditions: any typecheck or Vitest failure / Performance Target: N/A — build-time gate / Security Target: no runtime capability change / Acceptance Criteria: ACCEPT-BASE-001A/B / Excluded Behavior: disabling strict TypeScript / Dependencies: none.

### REQ-COMPAT-001 — Preserve v2 contracts

Priority: P0 / Mandatory: MUST / Actor: Existing v2 client / Trigger: v3 deployment candidate / Precondition: v2 contract fixtures / Input: v2 state/readiness/command requests / Input Validation: existing validators / Authorization: existing actor rules / Processing: run unchanged v2 handlers / Output: unchanged status, headers, and response shape / State Change: v2-compatible only / Side Effects: existing audit behavior / Failure Conditions: contract snapshot difference / Performance Target: no greater than 10% p95 regression in local benchmark / Security Target: no widened role / Acceptance Criteria: ACCEPT-COMPAT-001A/B / Excluded Behavior: v2 route removal / Dependencies: REQ-BASE-001.

### REQ-ACT-001 — Persist prioritized action items

Priority: P0 / Mandatory: MUST / Actor: Owner / Trigger: canonical business event or reconciliation / Precondition: authenticated workspace / Input: source kind, source ID, engagement ID, title, priority, due date, evidence refs / Input Validation: UUIDs, priority 1..5, non-empty title, existing source / Authorization: owner/operator; an assigned team member also needs `cwos.action.complete` for completion and can never dismiss / Processing: upsert by workspace+source+kind and increment version / Output: action item / State Change: OPEN→DONE or OPEN→DISMISSED only / Side Effects: append audit/outbox / Failure Conditions: stale version, cross-workspace source, missing evidence / Performance Target: overview p95 under 500 ms for 5,000 open items / Security Target: FORCE RLS / Acceptance Criteria: ACCEPT-ACT-001A/B/C/D / Excluded Behavior: deleting completed evidence / Dependencies: REQ-BASE-001.

### REQ-GOLD-001 — Golden Flow overview

Priority: P0 / Mandatory: MUST / Actor: Owner / Trigger: open `/v3` or request overview / Precondition: authenticated workspace / Input: optional as-of timestamp / Input Validation: ISO-8601 and bounded pagination / Authorization: workspace read permission / Processing: compose account, engagement, commitment, quote, delivery, finance, approvals, and action items from canonical records / Output: versioned overview / State Change: none / Side Effects: none / Failure Conditions: source unavailable, cross-workspace inconsistency, stale projection / Performance Target: p95 under 800 ms for pilot workspace / Security Target: field allow-list / Acceptance Criteria: ACCEPT-GOLD-001A/B / Excluded Behavior: canonical writes during read / Dependencies: REQ-ACT-001.

### REQ-GOLD-002 — Enforce active engagement next action

Priority: P0 / Mandatory: MUST / Actor: Owner / Trigger: engagement enters or remains ACTIVE / Precondition: engagement exists / Input: engagement transition / Input Validation: state transition contract / Authorization: owner/operator / Processing: require one OPEN commitment/action with due date / Output: transition result or conflict / State Change: engagement state and action projection in one transaction boundary / Side Effects: audit/outbox / Failure Conditions: no open action, stale version / Performance Target: p95 under 500 ms / Security Target: workspace scope / Acceptance Criteria: ACCEPT-GOLD-002A/B / Excluded Behavior: silent placeholder creation / Dependencies: REQ-ACT-001.

### REQ-GOLD-003 — Execute the complete Golden Flow

Priority: P0 / Mandatory: MUST / Actor: Owner / Trigger: controlled pilot scenario / Precondition: synthetic or consented pilot inquiry and PostgreSQL mode / Input: inquiry evidence, account, engagement, commitment, quote, approval, contract, delivery, purchase, financial item, settlement, renewal / Input Validation: each canonical resource contract and project/engagement linkage / Authorization: owner/operator; monetary and external decisions require human governance controls / Processing: advance each stage through existing canonical services and v3 composition routes / Output: one traceable engagement whose stages are COMPLETE or have an explicit blocker/action / State Change: canonical state transitions plus projection/outbox/audit / Side Effects: no external send/payment in autonomous test; adapter effects remain mocked at intent boundary / Failure Conditions: missing approval, next action, evidence, project key, or exact money reconciliation / Performance Target: E2E under 120 seconds in CI fixture / Security Target: workspace isolation and zero autonomous effect / Acceptance Criteria: ACCEPT-GOLD-003A/B / Excluded Behavior: prebuilding final fixture state without exercising transitions / Dependencies: REQ-GOLD-001, REQ-GOLD-002, REQ-FIN-001, REQ-APP-001.

### REQ-FIN-001 — Show settlement and cash risk

Priority: P0 / Mandatory: MUST / Actor: Owner / Trigger: overview read or financial/settlement event projection / Precondition: canonical financial items and settlements / Input: engagement ID or canonical event / Input Validation: canonical currency/amount invariants / Authorization: finance-read permission for overview; scoped worker capability for projector / Processing: overview performs a pure finance-service read; the idempotent event projector creates/updates a remediation action when a threshold is crossed / Output: finance summary with source IDs and a separately projected risk action / State Change: none on GET; projector changes only the derived action table / Side Effects: projector appends audit/outbox / Failure Conditions: money reconciliation mismatch, missing project key, stale event, or cross-workspace event / Performance Target: p95 under 800 ms / Security Target: no cross-workspace totals / Acceptance Criteria: ACCEPT-FIN-001A/B / Excluded Behavior: write during overview GET, statutory posting, or tax filing / Dependencies: REQ-ACT-001, REQ-GOLD-001.

### REQ-AI-001 — Evidence-bound AI proposal

Priority: P1 / Mandatory: MUST / Actor: AI/service principal / Trigger: owner asks for next action or risk proposal / Precondition: allow-listed evidence records / Input: proposal kind, engagement ID, evidence refs, model metadata, cost budget / Input Validation: evidence ownership and budget / Authorization: AI proposal permission only / Processing: create canonical PROPOSED suggestion with confidence and citations / Output: proposal record / State Change: PROPOSED→REVIEWED→ACCEPTED|REJECTED; EXPIRED is terminal / Side Effects: model invocation record / Failure Conditions: missing evidence, prompt-injection quarantine, budget exceeded / Performance Target: request timeout 30 s; no automatic retry after side-effect boundary / Security Target: no direct connector or finance write / Acceptance Criteria: ACCEPT-AI-001A/B / Excluded Behavior: AI approval of its own proposal / Dependencies: REQ-GOLD-001.

### REQ-APP-001 — Human approval before consequential effect

Priority: P0 / Mandatory: MUST / Actor: Owner / Trigger: proposal requests send, quote approval, purchase order, payment, deletion, or connector write / Precondition: valid proposal and governance control / Input: control ID, decision, expected version / Input Validation: unconsumed control, nonce/idempotency key / Authorization: human owner; step-up where configured / Processing: decide then consume exactly once / Output: decision and effect intent / State Change: PENDING→APPROVED|REJECTED→CONSUMED / Side Effects: audit/outbox only until an adapter executes / Failure Conditions: AI actor, replay, expired control, stale version / Performance Target: p95 under 500 ms / Security Target: fail closed / Acceptance Criteria: ACCEPT-APP-001A/B / Excluded Behavior: automatic approval / Dependencies: REQ-AI-001.

### REQ-CUT-001 — Reconcile import before cutover

Priority: P1 / Mandatory: MUST / Actor: Owner / Trigger: import plan validation or apply / Precondition: canonical `cwos_notion_import_plans` row, immutable source snapshot, and mapping / Input: plan ID, expected version, source counts, per-currency money totals, required-field failures, rejected rows, source hash / Input Validation: immutable source manifest and report hash / Authorization: import operator validates; human owner with approved governance control applies / Processing: reuse `PLANNED→APPROVED→APPLIED`; validation inserts an append-only `cwos_v3_reconciliation_reports` row and ordinary plan event, apply verifies the accepted report hash / Output: typed reconciliation report and canonical plan state / State Change: PLANNED→APPROVED only on exact reconciliation; APPROVED→APPLIED only after owner control / Side Effects: validation may write only plan/report/event evidence; no canonical business-entity import write occurs before APPLIED / Failure Conditions: any count/money/hash mismatch, unknown mapping, duplicate key, stale version, or missing control / Performance Target: 10,000 rows under 10 minutes in CI fixture / Security Target: no source secrets in report / Acceptance Criteria: ACCEPT-CUT-001A/B / Excluded Behavior: Notion and PostgreSQL dual source of truth / Dependencies: REQ-GOLD-001, REQ-FIN-001.

### REQ-OPS-001 — Controlled pilot release evidence

Priority: P0 / Mandatory: MUST / Actor: Release Reviewer / Trigger: v3 release candidate / Precondition: immutable commit and completed Golden Flow / Input: scenario key, evidence refs, metrics, open findings, gate results V0..V9 / Input Validation: evidence paths exist, commit matches, and every required gate has a typed result / Authorization: reviewer separate from code author / Processing: record each gate as PASS|FAIL|BLOCKED|NOT_RUN; pilot may be PASSED only when V0..V9 are PASS, while V10 is the resulting pilot acceptance and V11 remains a separate production approval / Output: typed gate manifest / State Change: pilot RUNNING→PASSED|FAILED|BLOCKED / Side Effects: none outside evidence storage / Failure Conditions: missing gate, any FAIL/BLOCKED/NOT_RUN, open CRITICAL/HIGH, failed restore, or unobserved CI / Performance Target: N/A — release gate / Security Target: redact secrets and personal data / Acceptance Criteria: ACCEPT-OPS-001A/B / Excluded Behavior: source completion equals production approval / Dependencies: all other MUST requirements.

- REQ-PORTAL-001: Portal/mobile clients can read allow-listed action status; full mobile authoring remains out of scope.
