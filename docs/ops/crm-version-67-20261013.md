## 배포 준비 산출물

`deploy/crm-deploy-master.sh`는 기존
`~/.local/state/omonyang/crm-deploy-1cf5.sh`를 기반으로 한다.
대상은 `CRM_TARGET_SHA`에 명시한 검수된 40자리 SHA로 고정한다.
1cf와 e91을 모두 선조로 포함하고 SQL delta가 없어야 한다.
최신 branch tip을 자동 선택하지 않는다. 아래 runtime 페이지 보정을
포함해야 하며, 옛 1cf를 그대로 빌드해 정적 화면을 배포하지 못하도록
실제 prerender manifest도 검사한다.

별도 승인 후 실행 순서:

1. 명시적 승인, Node 22, HTTPS origin 두 개, 대표가 등록한 새 private
   bcrypt state, 기존 e91 서비스와 drop-in을 검사한다.
2. 승인 SHA의 Git archive를 새 `app-<SHA 앞 8자리>`에 푼다. 아직 타깃 코드를 실행하지 않는다.
3. private `backups/pre-<SHA 앞 8자리>-*`에 custom-format `pg_dump`를 보관하고
   streaming hash와 목차를 확인한 다음, 네트워크 없는 임시 PostgreSQL에서
   password-free role 정의와 데이터 전체를 실제 복원한다.
   `pg_restore --exit-on-error --single-transaction --no-owner`가 성공해야 한다.
   덤프 전체를 메모리에 올리지 않는다. 검증 완료 뒤에만 frozen install,
   타깃 설정 validator와 웹 build를 실행한다. install/build는 격리 HOME과
   명시한 빌드 변수만 받으며 운영 DB 주소·키를 상속하지 않는다.
4. 기존 두 drop-in을 보관하고 SQL delta가 없음을 확인한 경우에만 API/web WorkingDirectory와 필요한
   설정을 전환한다. 설정은 릴리스 안의 mode600 환경파일을 마지막
   `EnvironmentFile=`로 추가해 적용한다. 기존 human env/signing key/auth state와
   review-ui는 건드리지 않는다.
5. API/web startup event, health/ready, `/login`, 빈 self-entry 요청의
   `400 INPUT_INVALID`를 확인한다. 두 서비스를 각각 검사하고 재시작한
   MainPID의 실효 인증 경로와 웹 설정까지 비교한 뒤에만 완료한다.
   systemctl WorkingDirectory와 실제 MainPID cwd도 새 릴리스와 대조한다.
   오류나 SIGHUP/SIGINT/SIGTERM이면 기존 drop-in으로 자동 롤백한다.

DB migration은 실행하지 않는다. dump는 보존하며 **운영 DB에는** 자동 restore하지
않는다. 임시 검증 DB/container는 종료 시 제거한다. 롤백은 기존 코드와 기존 인증 설정으로 복귀하는 절차이다.
새 인증 state를 삭제하거나 기존 state에 덮어쓰지 않는다.

이 문서의 배포 순서는 **후속 운영자용**이다. 이번 작업에서 승인 실행,
운영 백업/재시작/전환, 실제 로그인은 하지 않는다.

## CRM 7 등록: 대표 직접 단계

현재 등록 완료 여부를 비밀 파일을 열어서 추측하지 않는다. 대표가 직접
[기존 등록 절차](crm-own-login.md#owner-run-first-enrollment)를 수행하고
성공 여부만 운영자에게 전달한다. 기존
`~/.local/state/omonyang/crm-register-1cf5.md`도 같은 대상 커밋용 참고 문서다.

1. 승인된 private terminal에서 대상 커밋의
   `apps/api/src/operator-auth-enroll.mts`를 사용한다. 대표가 직접
   비밀번호와 OTP 앱을 준비하고, private 입력 파일과 **새 경로**의
   bcrypt state를 만든다. 에이전트는 비밀번호·seed·OTP·cookie를
   요청하거나 생성·수집하지 않는다.
2. 기존 scrypt state와 session signing key를 보존한다. 등록 CLI는
   기존 출력 파일을 거부한다. 성공 표시 `OPERATOR_ENROLLED`만 확인하고
   private 임시 입력은 대표가 정리한다. 등록에 사용한 OTP를 재사용하지 않는다.
3. 오모냥이 승인된 HTTPS web origin과 private identity API origin을
   확인한다. HTTP 주소, development 모드, Origin/CSRF 우회로 대신하지 않는다.
4. Cursor 검수와 별도 운영 승인 후에만 아래 스크립트를 실행한다.
   등록하지 않았거나 HTTPS 구성이 없으면 후속 배포가 차단되는 것이 정상이다.

후속 운영자가 준비할 변수:

| 변수 | 용도 |
| --- | --- |
| `CRM_TARGET_SHA` | 페이지 보정까지 포함해 검수한 정확한 40자리 commit |
| `CRM_WEB_ORIGIN` | 승인된 정확한 HTTPS browser origin |
| `OPERATOR_AUTH_API_BASE_URL` | 승인된 정확한 private HTTPS identity origin |
| `CWOS_V2_OPERATOR_AUTH_STATE_PATH` | 대표가 등록한 새 owner-only state 파일 |
| `CRM_APP_ENV`, `CRM_HUMAN_ENV` | 기본 private 운영 env 경로를 바꿀 때만 지정 |
| `CRM_BUILD_SLOT` | 선택 사항: 기존 build-slot wrapper의 실제 경로 |
| `CRM_NODE_BIN`, `CRM_PNPM_BIN` | 기본 Node 22.23.2와 같은 설치의 pnpm을 바꿀 때 지정 |

환경값과 키를 PR/로그에 붙이지 않는다. repo는 스크립트 상위 디렉터리로
자동 결정하며, 다른 source checkout을 사용할 때만 `CRM_REPO_ROOT`를 지정한다.

```sh
# 준비 검토용: 운영 변경 없음
bash deploy/crm-deploy-master.sh --help

# 다음 명령은 이번 작업에서 실행하지 않는다.
# 대표 등록 + HTTPS 구성 + Cursor 검수 + 별도 운영 승인 이후에만:
# CRM_TARGET_SHA는 위 조건을 통과한 실제 검수 SHA로 미리 지정한다.
: "${CRM_TARGET_SHA:?set the reviewed full SHA}"
CRM_DEPLOY_APPROVAL=approved CRM_TARGET_SHA="$CRM_TARGET_SHA" bash deploy/crm-deploy-master.sh
```

전환 후 대표가 직접 `/login`에서 로그인하고 `/v2/mail-candidate-review`,
CRM 6의 `/v2/quote-renewal`을 확인한다. 목록·원본 근거의 열람까지만
확인하고 확정/버리기, 초안 저장, 외부 발송, 결제는 별도 승인 범위다.

### 롤백과 수동 복구

첫 drop-in 쓰기 전에 자동 롤백을 활성화한다. startup/health/Origin
검사 실패는 보관한 `dropin-0`(API), `dropin-1`(web)을 원래 경로에
복원하고 daemon-reload/restart 후 각 unit의 is-active, 이전 실효 환경값,
WorkingDirectory와 MainPID cwd, API `/health`·`/ready`, web `/login`200과
같은 Origin 경계를 검사한다.
하나라도 실패하면 `changed`를 지우지 않으며 새 release와
backup을 보존하고 `ROLLBACK_INCOMPLETE`를 출력한다.
다중 unit의 `is-active` exit0을 전체 성공으로 쓰지 않는다.
`CRM_ROLLBACK_OK release=app-e91bb512`는 전체 runtime 검사 통과 표시이며,
대표 로그인 인수를 대신하지 않는다.
앞의 실측에서 e91에는 새 `/login` 페이지 파일이 없었다. 후속 운영에서
해당 HTTP 계약을 만족하지 못하면 파일 원복만으로 OK를 내지 않는다.
지시된 검사 목록을 줄이지 않고 `ROLLBACK_INCOMPLETE`와 자료 보존으로 남긴다.

SIGHUP/SIGINT/SIGTERM은 소유한 하위 프로세스 그룹에 종료를 요청하고 `close`를
기다린 다음 직렬로 롤백한다. 복구 중의 반복 신호가 복구를 끊지 않으며
완료 후 각각 exit129/130/143으로 종료한다. 일반 실패는 exit1이다.
TERM 후 5초에도 종료하지 않는 소유 프로세스 그룹에는 SIGKILL을 보내고
close를 확인한다. 반복 종료 요청으로 이 시한을 연장하지 않는다.
실효값 검사는 `/proc/<MainPID>/environ`에서 필요한 키만 비교하고 내용을
출력하지 않는다. `CRM_PROC_ROOT`는 격리 시험의 가짜 proc 경로용 override다.

`CRM_ROLLBACK_FAILED operator_action_required`가 나오면 새 릴리스와
private backup이 보존된다. 운영자가 실패 원인을 먼저 확인하고, 해당
실행의 정확한 `~/.local/share/core5/backups/pre-<대상 SHA 앞 8자리>-*` 하나를 선택한다.
그 안의 drop-in 두 개를 다음 원래 경로로 권한과 함께 복원한 후
두 서비스만 재시작한다. 이 수동 명령도 이번 작업에서 실행하지 않는다.

```sh
# CRM_BACKUP_DIR에는 실패한 실행의 정확한 backup 디렉터리를 지정한다.
: "${CRM_BACKUP_DIR:?select the exact backup for the failed run}"
cp --preserve=mode -- "$CRM_BACKUP_DIR/dropin-0" \
  "$HOME/.config/systemd/user/core5-api.service.d/90-crm-release.conf"
cp --preserve=mode -- "$CRM_BACKUP_DIR/dropin-1" \
  "$HOME/.config/systemd/user/core5-web.service.d/90-crm-release.conf"
systemctl --user daemon-reload
systemctl --user restart core5-api core5-web
systemctl --user is-active --quiet core5-api
systemctl --user is-active --quiet core5-web
systemctl --user show core5-api core5-web -p WorkingDirectory
curl --fail --silent --output /dev/null http://127.0.0.1:4312/health
curl --fail --silent --output /dev/null http://127.0.0.1:4312/ready
```

두 WorkingDirectory가 다시 e91 경로인지 확인한다. review-ui 재시작이나
DB restore, 키 회전은 이 절차에 포함되지 않는다.

## 초기 준비 검증 근거

아래 초기 격리 시험은 b7aefa1 시점의 제한된 검증이다. Cursor 검수에서
개별 서비스 상태, 신호 중단, EnvironmentFile 우선순위와 대용량 덤프를
놓친 것이 확인됐다. 현재 인수 근거는 뒤의 커밋된 회귀 시험이다.

| 시나리오 | 실행 / 관측 | 결과 |
| --- | --- | --- |
| Shell 문법 | `bash -n deploy/crm-deploy-master.sh` | exit 0 |
| 내장 Node 문법 | heredoc의 module을 Node 22.23.2 `--input-type=module --check` stdin에 전달 | exit 0 |
| 도움말 | `bash deploy/crm-deploy-master.sh --help` | exit 0, 준비 전용 안내 |
| 승인 없음 | `env -u CRM_DEPLOY_APPROVAL CRM_NODE_BIN=/does/not/exist bash deploy/crm-deploy-master.sh` | exit 1, `operator_approval_required`; Node 실행 전 차단 |
| 잘못된 인수 | `bash deploy/crm-deploy-master.sh --unexpected` | exit 64, `CRM_ARGUMENTS_REJECTED` |
| backup 실패 격리 실험 | 실제 스크립트의 dump 의존성을 exit 29로 실패시킴 | 서비스 전환/재시작 0회, 기존 파일 보존, 새 release/scratch 제거 |
| rollback 성공 격리 실험 | 실제 drop-in 전환 뒤 첫 daemon-reload를 exit 23으로 실패시킴 | 두 파일의 내용/권한 복원, private backup 보존, 새 release 제거 |
| rollback 실패 격리 실험 | 복구 daemon-reload도 실패시킴 | `CRM_ROLLBACK_FAILED`, 복구용 backup과 새 release 보존 |

격리 실험의 정확한 호출:

```sh
"$HOME/.nvm/versions/node/v22.23.2/bin/node" \
  "$HOME/.local/state/omonyang/TASK-CRM-VERSION-67-20261013/qa.mjs"
```

동일 디렉터리의 `intercept.mjs`가 systemctl/docker/pnpm을 격리한다.
실제 Git archive와 파일 I/O는 수행하며 dump는 **합성 bytes**이다.
실험은 세 시나리오 모두 PASS, exit 0으로 끝났고 각 sandbox를 삭제했다.
외부 명령의 예기치 않은 호출은 거부한다. 대표 인증 state나 키를 생성하지
않았고 실제 DB backup, 앱 build, 로그인, 운영 전환을 검증했다고 주장하지 않는다.

초기 변경은 shell script와 이 문서였으며, 이번 수정에는 회귀 시험도
포함한다. Shell LSP 오류 0개이며, 관련

범위 밖이므로 실행하지 않았다. out-of-repo QA `.mjs`의 LSP는 해당

## 두 번째 Cursor REJECT 수정

승인 뒤, 기준 상태를 읽기 전에 `CRM_UNIT_ROOT/.crm-deploy.lock`의
배타 `flock`을 잡는다. #65 진입점도 같은 파일을 사용한다. FD는 Node로
이어져 롤백과 정리까지 유지되고 종료 시 해제된다. lock 파일은 지우지
않아 inode 교체 경합을 만들지 않는다. 겹친 실행은 대기하거나 별도
snapshot을 만들지 않고 `deployment_in_progress`로 거부된다.

SIGHUP도 기존 신호 복구 경로에 포함했다. drop-in 마지막 LF가 없으면
구분 LF만 보충한 뒤 EnvironmentFile을 추가하며, 롤백은 원본의 LF 유무와
권한을 그대로 복원한다.

시험은 이제 호스트 저장소의 과거 커밋을 필요로 하지 않는다. Git 경계는
sandbox의 고정 응답과 최소 source tree로 모델링하고 실제 tar, script,
파일 I/O, OS 신호, flock을 실행한다. source mismatch와 SQL delta 거부도
회귀로 확인한다. production의 pin·Node 22 검사를 우회하지 않는다.

```sh

CI=1 PATH="$HOME/.nvm/versions/node/v20.20.2/bin:$PATH" \
```

시험 행렬로 돌아간다. 기본 checkout depth는 바꾸지 않았고 `deploy/**`
변경도 게이트를 실행한다.

## 네 번째 Cursor REJECT 수정

성공과 롤백이 같은 `verifyRuntime`을 호출한다. API health/ready200,

## 다섯 번째 Cursor REJECT 수정

모든 forward HTTP/runtime 검사를 `verifyRuntime`에 모았다. 복구도 같은
web `/login`200, Origin 입력 경계, API readiness, 각 unit 활성·환경·cwd를

백업은 목차 확인만으로 완료하지 않는다. 비밀번호를 제외한 role 정의를
보관하고, 네트워크 없는 소유 임시 cluster에 RLS 의존 role과 custom archive를
복원한다. 중단/실패도 container를 정리한다. 실제 PostgreSQL 16.11의
목차가 읽히는 반쪽 archive는 거부되고, 정상 archive는 합성 2,000행과
RLS policy를 복원했다. 데이터 검증 전에는 BACKUP_OK나 타깃 코드를 실행하지 않았다.

재현:
`CRM_TEST_PG_BIN=<설치한 PostgreSQL 16 bin 경로> node deploy/test/backup-restore.scenario.mjs master`.
이 호스트의 Docker socket은 접근 불가라 권한을 바꾸지 않고 소유 경로에
16.11을 빌드했다. 실제 SQL/restore 절차는 native backend로 실행했으며
Docker daemon의 기동 자체를 검증했다고 주장하지 않는다.

`/`, `/work`, `/pilot`, `/approvals`, `/monitor`, `/v2`는 force-dynamic이다.
빌드에는 운영 비밀을 넣지 않으며, 명시한 네 public 변수는 보존하고
빈 NEXT_PUBLIC 값을 강제로 넣지 않는다. 빌드 manifest에 여섯 경로가
정적 route로 남으면 서비스 변경 전에 거부한다. 이 보정을 실제 archive에
포함시키기 위해 #65와 같은 명시적 SHA/선조 검증을 적용했다.

실제 설정 없는 production build에서 여섯 경로가 static → dynamic으로 바뀌었다.
