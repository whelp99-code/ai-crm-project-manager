## 배포 준비 산출물

`deploy/crm-deploy-master.sh`는 기존
`~/.local/state/omonyang/crm-deploy-1cf5.sh`를 기반으로 한다.
대상 SHA는 위 master snapshot으로 고정한다. 실행 시 임의의 최신 커밋을
가져와 승인된 대상 대신 배포하지 않는다. master가 바뀌면 운영자가
차이와 SQL 변경을 다시 검토하고 대상 pin을 새 PR에서 갱신한다.

별도 승인 후 실행 순서:

1. 명시적 승인, Node 22, HTTPS origin 두 개, 대표가 등록한 새 private
   bcrypt state, 기존 e91 서비스와 drop-in을 검사한다.
2. 고정 Git archive를 새 `app-1cf53882`에 풀고 frozen dependency 설치,
   대상 버전의 설정 validator, 웹 build를 수행한다.
3. private `backups/pre-1cf5-*`에 custom-format `pg_dump`를 보관하고
   `pg_restore --list`로 읽을 수 있는지 검사한다. 기존 두 drop-in도 보관한다.
4. SQL delta가 없음을 확인한 경우에만 API/web WorkingDirectory와 필요한
   설정을 전환한다. review-ui와 기존 signing key/auth state는 건드리지 않는다.
5. API/web startup event, health/ready, `/login`, 빈 self-entry 요청의
   `400 INPUT_INVALID`를 확인한다. 이후 오류면 기존 drop-in으로 자동 롤백한다.

DB migration은 실행하지 않는다. dump는 보존하며 DB를 자동 restore하지
않는다. 롤백은 기존 코드와 기존 인증 설정으로 복귀하는 절차이다.
새 인증 state를 삭제하거나 기존 state에 덮어쓰지 않는다.

이 문서의 배포 순서는 **후속 운영자용**이다. 이번 작업에서 승인 실행,
운영 백업/재시작/전환, 실제 로그인은 하지 않는다.

## CRM 7 등록: 대표 직접 단계

현재 등록 완료 여부를 비밀 파일을 열어서 추측하지 않는다. 대표가 직접
[기존 등록 절차](crm-own-login.md#owner-run-first-enrollment)를 수행하고
성공 여부만 운영자에게 전달한다. 기존
`~/.local/state/omonyang/crm-register-1cf5.md`도 같은 대상 커밋용 참고 문서다.

1. 승인된 private terminal에서 대상 커밋의
   `apps/api/src/operator-auth-enroll.mts`를 사용한다. 대표가 직접
   비밀번호와 OTP 앱을 준비하고, private 입력 파일과 **새 경로**의
   bcrypt state를 만든다. 에이전트는 비밀번호·seed·OTP·cookie를
   요청하거나 생성·수집하지 않는다.
2. 기존 scrypt state와 session signing key를 보존한다. 등록 CLI는
   기존 출력 파일을 거부한다. 성공 표시 `OPERATOR_ENROLLED`만 확인하고
   private 임시 입력은 대표가 정리한다. 등록에 사용한 OTP를 재사용하지 않는다.
3. 오모냥이 승인된 HTTPS web origin과 private identity API origin을
   확인한다. HTTP 주소, development 모드, Origin/CSRF 우회로 대신하지 않는다.
4. Cursor 검수와 별도 운영 승인 후에만 아래 스크립트를 실행한다.
   등록하지 않았거나 HTTPS 구성이 없으면 후속 배포가 차단되는 것이 정상이다.

후속 운영자가 준비할 변수:

| 변수 | 용도 |
| --- | --- |
| `CRM_WEB_ORIGIN` | 승인된 정확한 HTTPS browser origin |
| `OPERATOR_AUTH_API_BASE_URL` | 승인된 정확한 private HTTPS identity origin |
| `CWOS_V2_OPERATOR_AUTH_STATE_PATH` | 대표가 등록한 새 owner-only state 파일 |
| `CRM_APP_ENV`, `CRM_HUMAN_ENV` | 기본 private 운영 env 경로를 바꿀 때만 지정 |
| `CRM_BUILD_SLOT` | 선택 사항: 기존 build-slot wrapper의 실제 경로 |
| `CRM_NODE_BIN`, `CRM_PNPM_BIN` | 기본 Node 22.23.2와 같은 설치의 pnpm을 바꿀 때 지정 |

환경값과 키를 PR/로그에 붙이지 않는다. repo는 스크립트 상위 디렉터리로
자동 결정하며, 다른 source checkout을 사용할 때만 `CRM_REPO_ROOT`를 지정한다.

```sh
# 준비 검토용: 운영 변경 없음
bash deploy/crm-deploy-master.sh --help

# 다음 명령은 이번 작업에서 실행하지 않는다.
# 대표 등록 + HTTPS 구성 + Cursor 검수 + 별도 운영 승인 이후에만:
CRM_DEPLOY_APPROVAL=approved bash deploy/crm-deploy-master.sh
```

전환 후 대표가 직접 `/login`에서 로그인하고 `/v2/mail-candidate-review`,
CRM 6의 `/v2/quote-renewal`을 확인한다. 목록·원본 근거의 열람까지만
확인하고 확정/버리기, 초안 저장, 외부 발송, 결제는 별도 승인 범위다.

### 롤백과 수동 복구

첫 drop-in 쓰기 전에 자동 롤백을 활성화한다. startup/health/Origin
검사 실패는 보관한 `dropin-0`(API), `dropin-1`(web)을 원래 경로에
복원하고 daemon-reload/restart/is-active를 수행한다.
`CRM_ROLLBACK_OK release=app-e91bb512`는 명령 완료 표시이며,
대표 로그인 인수를 대신하지 않는다.

`CRM_ROLLBACK_FAILED operator_action_required`가 나오면 새 릴리스와
private backup이 보존된다. 운영자가 실패 원인을 먼저 확인하고, 해당
실행의 정확한 `~/.local/share/core5/backups/pre-1cf5-*` 하나를 선택한다.
그 안의 drop-in 두 개를 다음 원래 경로로 권한과 함께 복원한 후
두 서비스만 재시작한다. 이 수동 명령도 이번 작업에서 실행하지 않는다.

```sh
# CRM_BACKUP_DIR에는 실패한 실행의 정확한 backup 디렉터리를 지정한다.
: "${CRM_BACKUP_DIR:?select the exact backup for the failed run}"
cp --preserve=mode -- "$CRM_BACKUP_DIR/dropin-0" \
  "$HOME/.config/systemd/user/core5-api.service.d/90-crm-release.conf"
cp --preserve=mode -- "$CRM_BACKUP_DIR/dropin-1" \
  "$HOME/.config/systemd/user/core5-web.service.d/90-crm-release.conf"
systemctl --user daemon-reload
systemctl --user restart core5-api core5-web
systemctl --user is-active core5-api core5-web
systemctl --user show core5-api core5-web -p WorkingDirectory
curl --fail --silent --output /dev/null http://127.0.0.1:4312/health
curl --fail --silent --output /dev/null http://127.0.0.1:4312/ready
```

두 WorkingDirectory가 다시 e91 경로인지 확인한다. review-ui 재시작이나
DB restore, 키 회전은 이 절차에 포함되지 않는다.

## 준비 검증 근거

| 시나리오 | 실행 / 관측 | 결과 |
| --- | --- | --- |
| Shell 문법 | `bash -n deploy/crm-deploy-master.sh` | exit 0 |
| 내장 Node 문법 | heredoc의 module을 Node 22.23.2 `--input-type=module --check` stdin에 전달 | exit 0 |
| 도움말 | `bash deploy/crm-deploy-master.sh --help` | exit 0, 준비 전용 안내 |
| 승인 없음 | `env -u CRM_DEPLOY_APPROVAL CRM_NODE_BIN=/does/not/exist bash deploy/crm-deploy-master.sh` | exit 1, `operator_approval_required`; Node 실행 전 차단 |
| 잘못된 인수 | `bash deploy/crm-deploy-master.sh --unexpected` | exit 64, `CRM_ARGUMENTS_REJECTED` |
| backup 실패 격리 실험 | 실제 스크립트의 dump 의존성을 exit 29로 실패시킴 | 서비스 전환/재시작 0회, 기존 파일 보존, 새 release/scratch 제거 |
| rollback 성공 격리 실험 | 실제 drop-in 전환 뒤 첫 daemon-reload를 exit 23으로 실패시킴 | 두 파일의 내용/권한 복원, private backup 보존, 새 release 제거 |
| rollback 실패 격리 실험 | 복구 daemon-reload도 실패시킴 | `CRM_ROLLBACK_FAILED`, 복구용 backup과 새 release 보존 |

격리 실험의 정확한 호출:

```sh
"$HOME/.nvm/versions/node/v22.23.2/bin/node" \
  "$HOME/.local/state/omonyang/TASK-CRM-VERSION-67-20261013/qa.mjs"
```

동일 디렉터리의 `intercept.mjs`가 systemctl/docker/pnpm을 격리한다.
실제 Git archive와 파일 I/O는 수행하며 dump는 **합성 bytes**이다.
실험은 세 시나리오 모두 PASS, exit 0으로 끝났고 각 sandbox를 삭제했다.
외부 명령의 예기치 않은 호출은 거부한다. 대표 인증 state나 키를 생성하지
않았고 실제 DB backup, 앱 build, 로그인, 운영 전환을 검증했다고 주장하지 않는다.

변경은 shell script와 이 문서뿐이다. Shell LSP 오류 0개이며, 관련
TypeScript 변경과 프로젝트 lint 명령은 없다. 전체 앱 테스트/빌드는
범위 밖이므로 실행하지 않았다. out-of-repo QA `.mjs`의 LSP는 해당
디렉터리에 TypeScript 설치가 없어 초기화되지 않았으며 Node 문법 검사와
실행 assertion으로 검증했다.

QA 후 동일한 systemd 조회에서 API/web/review-ui의 PID
`20475`/`20478`/`20477`, WorkingDirectory, active/running 상태가 모두
시작 전과 같았다. `/tmp/crm-version67-*` sandbox 잔존 경로는 0개였다.

최종 인계는 non-draft PR의 정확한 head를 대상으로 한다. 실제 배포와
대표 인수는 후속 단계이며, Project 상태는 Cursor 검수를 위한 Verify에 둔다.
